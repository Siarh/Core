DPScope — локальный AI-компаньон через Ollama / Qwen
=======================================================

AI-компаньон работает на этом же ПК через локальный Ollama API
(http://localhost:11434). Внешний AI-сервис, OpenAI API и API-ключ не нужны.
По умолчанию используется qwen3.5:27b; можно выбрать qwen3.5:9b.

1. Проверка Ollama
------------------
Убедись, что Ollama запущена. Открой PowerShell в папке tools:

  cd "C:\Games\Allods Online\data\Mods\Addons\DPScope\tools"
  ollama list
  python aou_ai_companion.py --check-ollama

Путь в команде cd замени на фактический путь к папке DPScope\tools.

Если модель ещё не установлена, загрузи её один раз:

  ollama pull qwen3.5:27b

Для менее требовательного варианта:

  ollama pull qwen3.5:9b

2. Рекомендуемый способ: чтение журнала напрямую из user.cfg
-------------------------------------------------------------
DPScope сохраняет события в конфигурацию аддона. После полного закрытия игры
журнал находится в файле:

  <папка Allods Online>\data\Mods\Configs\DPScope\user.cfg

В старых конфигурациях также может использоваться Personal\user.cfg.
Извлекатель сначала ищет отдельный конфиг DPScope, а затем старый общий файл.

Закрой игру штатно, чтобы клиент успел записать user.cfg на диск. Затем в
PowerShell из папки tools выполни одну команду:

  python aou_extract_usercfg.py "C:\Games\Allods Online"

Замени путь на корневую папку своей игры. Можно передать и полный путь к файлу:

  python aou_extract_usercfg.py "C:\Games\Allods Online\data\Mods\Configs\DPScope\user.cfg"

Извлекатель работает только на чтение: не меняет, не очищает и не перезаписывает
user.cfg. Он извлекает aou_evt_count и aou_evt_1...aou_evt_N, проверяет наличие
всех записей и их структуру, создаёт локальную AOUCSV-выгрузку и запускает
обычный конвейер профиля/калькулятора/локальной Qwen.

Поддерживаются схемы v1, v2 и актуальная v3. Старые строки автоматически
нормализуются в памяти: v1 получает пустые actor_id/target_id/stat_sample_age,
v2 сохраняет эти поля, но получает пустые entity descriptors. Ничего отсутствующего
не выдумывается; user.cfg остаётся только для чтения. Повторный запуск извлечения и анализа всех сохранённых событий:

  python aou_extract_usercfg.py "C:\Games\Allods Online" --overwrite

--overwrite заменяет только AOUCSV и результаты в DPScope_UserCfg_Export,
не исходный user.cfg.

Результаты появятся в папке:

  <папка Allods Online>\DPScope_UserCfg_Export\

Там будут исходный текстовый экспорт и подпапка analysis с файлами:

  AoU_combat_log.csv       восстановленный журнал;
  aou_event_profile.json   профиль событий;
  aou_report.json          детерминированный расчёт DPScope;
  aou_ai_payload.json      компактная сводка, переданная локальной модели;
  aou_ai_advice.md         ответ Qwen на русском языке.

Если нужно проверить чтение и построение профиля без запуска Ollama:

  python aou_extract_usercfg.py "C:\Games\Allods Online" --prepare-only

Если результаты уже существуют, добавь --overwrite. Это заменяет только
выходные файлы в DPScope_UserCfg_Export; исходный user.cfg не изменяется.

3. Резервный способ: OCR-экспорт из игрового чата
------------------------------------------------
Прямое чтение user.cfg предпочтительно. Если конфиг отсутствует или в нём нет
сохранённого журнала, можно использовать экспорт через чат:

  /aou eventfile 1000 1

Он разбит на страницы по 10 событий, чтобы не перегружать игровой клиент.
Сохрани каждую страницу скриншотами, распознай OCR и собери строки всех страниц
в один UTF-8 TXT. Затем запусти:

  python aou_ai_companion.py "D:\Logs\aou_eventfile_ocr.txt"

Повторные заголовки и BEGIN/END оставляй: конвертер сам соберёт общий журнал и
откажется анализировать выгрузку, если каких-либо записей не хватает.

Чтобы повторно проанализировать уже сохранённый AOUCSV-экспорт (например,
aou_usercfg_export.txt на 1000 событий), запусти из папки tools:

  python aou_ai_companion.py "D:\Logs\DPScope_UserCfg_Export\aou_usercfg_export.txt" --overwrite --model qwen3.5:4b

Укажи свой фактический путь. --overwrite заменяет только выходные JSON/MD/CSV
в папке результатов; входной TXT не изменяется. Конвертер проверит, что все
1000 R-записей присутствуют, затем заново построит профиль, ME, формульные
кривые и AI-payload. В payload попадут все рассчитанные ME comparison rows,
но не сырые события и не actor/target IDs.

В консольном отчёте проверь:
- восстановлено / ожидается — например 1000 / 1000;
- source_rows и combat_rows;
- сколько событий включено в контролируемую ME;
- число strict и legacy_exploratory сравнений;
- total_comparisons и comparisons_included_in_ai_payload.
Если strict=0, а legacy больше нуля, AI анализирует старые строки только
как гипотезы с VERY_LOW confidence. Для строгой проверки нужно записать новые
события актуальной версией аддона.

4. Анализ смены характеристик
------------------------------
Изменение M/R/U/L между боями не считается ошибкой. Каждое событие
нормализуется по записанному рядом снимку характеристик; медианные значения
используются только как общий ориентир для расчётного оптимизатора.

В aou_event_profile.json и aou_ai_payload.json есть две разные сводки:

**stat_comparison** — описательные суммы/скорости по отдельным режимам (damage,
healing, incoming), профилям PvE/PvP и полному снимку восьми характеристик
M/R/U/L/S/W/B/C. Это не причинный эффект.

**controlled_stat_efficiency** — строгий фильтр для экспериментальных сравнений.
Он сопоставляет только одинаковые контексты: PvE/PvP, длительность боя,
способность, элемент, источник урона, диапазон HP, качество HP-сэмпла,
диапазон Решимости, Normal/Critical и получателя лечения. Между baseline и test
должна измениться одна характеристика минимум на 25 очков или 3%, остальные
сохранённые характеристики должны оставаться в допуске. На каждом наборе нужно
не менее 3 независимых боёв и 3 событий в выбранном контексте каждого боя.
Внутри одного боя изменение снимка статов помечает бой как contaminated и
исключает его из строгого сравнения. Снимок статов обновляется не чаще одного
раза в 3 секунды; переключение статов и возврат к исходным значениям между
двумя снимками может остаться незамеченным. События со слишком старым
stat_sample_age исключаются из контролируемой ME.

Главный принцип анализа — **Marginal Efficiency**:
`ME = ΔResult / ΔStat = (Result_test - Result_base) / (Stat_test - Stat_base)`.
Для удобства также показывается `ME_100 = ME * 100`. В каждом сравнении
сохраняются обе исходные величины, `delta_result`, `delta_stat`, ME за +1
стат и ME за +100. Для входящего урона отрицательная ME означает уменьшение
получаемого урона и благоприятный защитный эффект; для damage/healing
положительная ME означает увеличение результата.

Основная ME теперь рассчитывается как разница объёма совпавшего контекста
способности за секунду полного таймера боя, делённая на изменение характеристики
и приведённая к +100 очкам. Дополнительно сохраняются средний размер события,
число событий, число независимых боёв и bootstrap 95% CI по per-fight rates.
Для Мастерства/Решимости/Беспощадности Normal и Critical анализируются отдельно.
Для Удачи Normal+Critical объединяются в scope=all_hits, чтобы учитывать
наблюдаемое изменение доли критов. Это rate одной способности в совпавшем
контексте, не полный DPS/HPS персонажа. Статус результата — DERIVED /
controlled-observational, а не доказанная причинность.
actor_id/target_id записываются только при наличии примитивного instance ID из
callback; имя или путь resource-шаблона не считается идентификатором экземпляра.
Новые v3 строки дополнительно содержат actor/target name, level, quality и is_mob.
Для исходящего damage анализатор сопоставляет разные target instance IDs по
signature цели, а для incoming — разные actor instance IDs по signature атакующего.
В обоих случаях signature требует нормализованное имя, уровень, элитность и признак
моба. Для healing получатель остаётся привязан к точному instance ID. Исходные
instance IDs сохраняются и по-прежнему обязательны вместе со свежим stat_sample_age
для strict evidence. Entity signature — приближённый archetype key, а не уникальный
серверный template ID: одинаковые имя/уровень/элитность могут соответствовать
разным вариантам существа. При неполной метаинформации анализатор использует точный
instance ID и не объединяет разные экземпляры по одному имени.
Если ID или stat_sample_age отсутствуют (legacy v1), строка не теряется:
она попадает в отдельный слой legacy_exploratory с confidence=VERY_LOW.
Такие строки не смешиваются со strict-сравнениями. IDs остаются в локальном
профиле для сопоставления, но не передаются в Ollama payload.
Идентификатор и archetype signature не раскрывают полное состояние цели.
Баффы/дебаффы, таланты и ротация по каждому событию пока не сохраняются, поэтому
даже совпавшая signature не доказывает полное совпадение боевых условий.
Для лечения это reported healing per event, не Effective HPS: callback не
содержит достоверный overheal для всех событий. Если данных мало, вывод —
INSUFFICIENT DATA, а не рейтинг статов.

AI payload содержит все рассчитанные ME comparison rows, без прежнего ограничения
первых 25. В профиле и payload сверяй:
- export_records_expected / export_records_reconstructed;
- source_rows / combat_rows / included_events;
- input_event_rows / validated_event_rows_before_contamination;
- total_comparisons / strict_comparison_count / legacy_exploratory_comparison_count.
Если в исходном экспорте 1000 событий, AI обязан увидеть факт 1000 восстановленных
записей и сообщить, сколько из них вошло в ME, сколько исключено и почему.
Strict ME и legacy exploratory ME никогда не объединяются:
старые v1 записи без instance IDs или возраста снимка дают только
legacy_exploratory с VERY_LOW confidence. Не ранжируй их наравне со strict.

**temporal_performance** — агрегирует callback-события по секундам полного таймера
каждого боя. Считает максимальные скользящие окна 1/3/5/10/15/30 сек и лучшие
30/60/120/180/300-секундные окна отдельно для damage/healing/incoming. Тихие
секунды заполняются нулями; если бой короче окна, статус — insufficient_duration.
Это reported/raw callback rate (DERIVED), не Effective DPS/HPS и не отдельная
скорость применения способности.

Resolve summary сначала усредняет значения пула внутри каждой секунды, затем
показывает среднее/медиану/пик и долю sampled seconds выше 25/50/75/90%.
Это доля секунд, в которых были события и замер Решимости, а не непрерывный
time-above-threshold или Resolve uptime. PvE/PvP приходит из выбранного профиля,
не является автоматически выведенной классификацией игры.

**event_effectiveness** хранит две отдельные величины:
- reported_amount/rate — сумма amount из callback;
- estimated_effective_amount/rate — min(reported amount, оставшийся HP для damage
  или недостающий HP для healing), когда перед событием известны HP и max HP;
- estimated_excess_amount — estimated overkill/overheal.

Эта capped оценка имеет классификацию ESTIMATED: API не даёт достоверный
target_hp_after и полную очередность щитов/поглощений/модификаторов. События без
HP сохраняются в reported_total, но не входят в estimated_effective_total.
Поэтому не называй этот расчёт точным Effective DPS/HPS.

**critical_analysis** — сводка по способности/элементу/HP- и Resolve-фазе:
флаги обычных/критических событий и суммы из callback — MEASURED;
crit rate, доля суммы от критов и отношение средних — DERIVED descriptive.
Наблюдаемое отношение не является доказанным универсальным critical multiplier:
условия цели, баффы и фазы могут различаться.

Сами actor_id/target_id сохраняются только в локальном профиле для сопоставления;
их значения не передаются в Ollama payload.

Медианный снимок статов служит только входом теоретического калькулятора.
Он не заменяет контролируемое сравнение. УВС, лечение и входящий урон не
складываются в один показатель.

**model_marginal_efficiency** — теоретическая чувствительность формул, всегда
помечена ESTIMATED. Для текущего набора событий калькулятор пересчитывает
результат при +100/+200/+300/+400 к каждой поддерживаемой характеристике и
показывает изменение результата на +100, относительный прирост, кандидата
soft-knee и парные взаимодействия X+Y. Положительное взаимодействие означает
synergy внутри формулы, отрицательное — competition внутри формулы; это не
эмпирическое доказательство серверной механики.

Для этой оценки сохраняются неизменными последовательность событий, состав
способностей, HP-фазы и записанный пул Решимости каждого события. Поэтому она
не моделирует повторное накопление Решимости для нового билда. Удача считается
по ожидаемому шансу крита и базовому x2; наблюдаемые средние крит/обычный удар
остаются описательными и не подменяют критический коэффициент формулы.
Кривая Беспощадности не строится при пропусках HP цели; Выносливость требует
class_k; Воля требует PvP control_windows и control_weight. Характеристики без
подтверждённой формулы остаются в реестре как unsupported, без выдуманного ME.

Система поэтому сохраняет два разных уровня вывода:
- DERIVED — сопоставленные боевые наблюдения с повторными независимыми боями;
- ESTIMATED — конечная разность математической модели при фиксированных
  событиях и допущениях формулы.

MEASURED относится только к самим полям журнала, которые действительно пришли
из игрового callback. Ни DERIVED, ни ESTIMATED не следует называть MEASURED
эффектом характеристики.

4. Настройки анализа
--------------------
По умолчанию используется qwen3.5:27b. Для меньшей модели:

  python aou_extract_usercfg.py "C:\Games\Allods Online" --model qwen3.5:9b

Если бюджет свободных очков отличается от 20, укажи его явно:

  python aou_extract_usercfg.py "C:\Games\Allods Online" --budget 15

Коэффициент Решимости по умолчанию 0.015 — буквальное значение формулы,
которое использует текущий профиль импортера. Альтернативное 0.0015 можно
задать параметром --resolve-coefficient 0.0015; это другая трактовка, а не
автоматически подтверждённое значение.

5. Приватность и границы работы
-------------------------------
- Запрос к модели отправляется только локальному Ollama на этом ПК.
- OPENAI_API_KEY и другие облачные API-ключи не используются.
- В модель передаётся компактная сводка расчёта, без сырых строк журнала,
  названий способностей и идентификаторов целей/игроков.
- aou_ai_payload.json позволяет проверить, какие именно данные получила модель.
- Первичная загрузка через ollama pull требует интернет; после этого анализ
  выполняется локально.
- Lua-аддон Allods не запускает Python и не обращается к Ollama напрямую.
  Встроенная команда /aou ai on/off управляет только игровым детерминированным
  советником, а не отдельным desktop-компаньоном.
- Вывод Qwen объясняет результаты калькулятора и качество выборки; это не
  доказательство игровых формул и не замена проверке в клиенте Allods.
